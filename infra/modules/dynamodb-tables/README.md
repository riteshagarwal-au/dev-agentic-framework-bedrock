# dynamodb-tables

Provisions the 4 DynamoDB tables backing DAF Phase 1's run-persistence layer, per design.md Data
Models ("Model 1: RunConfig/RunState", "Model 2: RunCounters", "Model 3: HitlGateTicket") and
Requirements 8.1 and 8.3.

## What this module creates

| Table | Partition key | GSI | Billing mode | Python repository |
|---|---|---|---|---|
| **RunState** | `runId` (S) | — | `PAY_PER_REQUEST` | `RunStateRepository` (Task 5.2) |
| **RunCounters** | `runId` (S) | — | `PAY_PER_REQUEST` | `RunCountersRepository` (Task 5.3) |
| **GateTicket** | `ticketId` (S) | `runId-index` on `runId` (S) | `PAY_PER_REQUEST` | `GateTicketRepository` (Task 5.4) |
| **DeadLetterRecord** | `deadLetterId` (S) | `runId-index` on `runId` (S) | `PAY_PER_REQUEST` | `DeadLetterRecordRepository` (Task 5.5) |

All 4 tables have:

- **On-demand billing** (`PAY_PER_REQUEST`) — appropriate for Phase 1's unpredictable, low-scale
  usage; no capacity planning/autoscaling needed.
- **Point-in-time recovery** enabled (`var.point_in_time_recovery_enabled`, default `true`).
- **Server-side encryption** via KMS (`server_side_encryption { enabled = true, kms_key_arn = ... }`),
  using either a KMS key this module creates (`create_kms_key = true`, the default) or an existing
  key ARN passed in (`create_kms_key = false` + `kms_key_arn`) — the same create-or-reuse pattern
  used by `modules/state-backend`.

An optional dedicated KMS key + alias is created when `create_kms_key = true`.

## Key schema rationale

### RunState: `runId`-only partition key, `currentStepIndex` as a plain attribute

The task description phrases this as "RunState by `runId` (+ `currentStepIndex` attribute)" —
`currentStepIndex` is an **attribute**, not a sort key. `RunState` (design.md Model 1) is a single
evolving item per run (one `runId` → one item holding `taskGraph`, `currentStepIndex`, `counters`,
`status`, etc., see `backend/src/daf/models/run.py`), not a growing collection of per-step-boundary
items. `RunStateRepository`'s (Task 5.2) idempotent per-step-boundary write is implemented as a
conditional `PutItem`/`UpdateItem` against that one item (e.g. conditioned on the item's current
`currentStepIndex` matching the expected prior value), not via a composite `runId + stepIndex` key.
A `runId`-only partition key is sufficient and simpler.

### GateTicket and DeadLetterRecord: dedicated ID partition key + `runId` GSI

Both tables are collections (many tickets/dead-letters per run), so each needs its own generated
primary key (`ticketId`, `deadLetterId`) for direct lookup, plus a `runId` GSI for the "all items
for this run" access pattern:

- `getPendingGates(runId)` (Task 9.3) queries the GateTicket table's `runId-index`.
- The DeadLetterRecord list-by-run operation (Task 5.5) queries the DeadLetterRecord table's
  `runId-index`.

`deadLetterId` is generated by the repository layer (e.g. `uuid4()` in `DeadLetterRecordRepository`,
Task 5.5) at write time — **not** by DynamoDB itself (DynamoDB has no auto-generated key feature).

### GSI projection type

Both GSIs default to `projection_type = "ALL"` (`var.gsi_projection_type`) so a query against the
GSI returns the full item without a follow-up `GetItem` against the base table. At Phase 1 scale
this is simplest and the storage/throughput cost of projecting the whole item is negligible.
Override to `"KEYS_ONLY"` or `"INCLUDE"` if a later phase needs a narrower projection.

## Usage

```hcl
module "dynamodb_tables" {
  source      = "../../modules/dynamodb-tables"
  environment = var.environment
}
```

```hcl
output "run_state_table_name" {
  value = module.dynamodb_tables.run_state_table_name
}

output "dynamodb_table_arns" {
  value = module.dynamodb_tables.table_arns
}
```

### Reusing an existing KMS key

```hcl
module "dynamodb_tables" {
  source         = "../../modules/dynamodb-tables"
  environment    = var.environment
  create_kms_key = false
  kms_key_arn    = module.state_backend.kms_key_arn
}
```

## Downstream consumers

- **Tasks 5.2-5.5 (Python repository layer)**: each repository (`RunStateRepository`,
  `RunCountersRepository`, `GateTicketRepository`, `DeadLetterRecordRepository`) reads its target
  table name from configuration/environment variables populated from this module's
  `table_names` output (or the individual `*_table_name` outputs).
- **Task 3.4 (per-agent IAM roles)** / any Lambda execution role needing DynamoDB access: IAM
  policy `Resource` lists reference this module's `table_arns` output (or the individual
  `*_table_arn` outputs, plus `"${arn}/index/*"` for GSI query access on GateTicket and
  DeadLetterRecord).

## Inputs

| Name | Description | Type | Default |
|---|---|---|---|
| `environment` | Environment/target name; namespaces table names/tags. | `string` | n/a (required) |
| `name_prefix` | Prefix for generated table names. | `string` | `"daf-phase1"` |
| `create_kms_key` | Whether to create a dedicated KMS key. | `bool` | `true` |
| `kms_key_arn` | Existing KMS key ARN to use when `create_kms_key = false`. | `string` | `null` |
| `kms_key_deletion_window_in_days` | KMS key deletion window. | `number` | `30` |
| `gsi_projection_type` | Projection type for the `runId` GSIs on GateTicket/DeadLetterRecord. | `string` | `"ALL"` |
| `point_in_time_recovery_enabled` | Whether PITR is enabled on all 4 tables. | `bool` | `true` |
| `deletion_protection_enabled` | Whether DynamoDB deletion protection is enabled on all 4 tables. | `bool` | `false` |
| `tags` | Extra tags merged onto all resources. | `map(string)` | `{}` |

## Outputs

| Name | Description |
|---|---|
| `run_state_table_name` / `run_state_table_arn` | RunState table name/ARN. |
| `run_counters_table_name` / `run_counters_table_arn` | RunCounters table name/ARN. |
| `gate_ticket_table_name` / `gate_ticket_table_arn` | GateTicket table name/ARN. |
| `gate_ticket_run_id_gsi_name` | Name of the GateTicket table's `runId` GSI (`"runId-index"`). |
| `dead_letter_record_table_name` / `dead_letter_record_table_arn` | DeadLetterRecord table name/ARN. |
| `dead_letter_record_run_id_gsi_name` | Name of the DeadLetterRecord table's `runId` GSI (`"runId-index"`). |
| `kms_key_arn` | ARN of the KMS key used to encrypt all 4 tables. |
| `table_arns` | Map of all 4 table ARNs keyed by `run_state` / `run_counters` / `gate_ticket` / `dead_letter_record`. |
| `table_names` | Map of all 4 table names keyed by the same 4 keys. |

## Requirements traceability

- **Requirement 8.1**: "WHEN a run transitions between task-graph steps THEN the updated
  `RunState` (including `taskGraph`, `currentStepIndex`, and `counters`) SHALL be persisted before
  the next step begins." — the RunState and RunCounters tables provisioned here are the durable
  store `RunStateRepository`/`RunCountersRepository` (Tasks 5.2/5.3) write to before each step
  begins; this module provisions the tables, the repository layer enforces the write-before-next-
  step ordering.
- **Requirement 8.3**: "...persist the failed invocation's context (task envelope reference, error
  detail, retry count, trace ID) as a dead-letter record in a durable store (DynamoDB) rather than
  discarding it..." — the DeadLetterRecord table provisioned here is that durable store;
  `DeadLetterRecordRepository` (Task 5.5) and the retry-exhaustion path (Task 10.4) are responsible
  for actually writing to it.
